# ADR 0012: Rewards, learning, item swaps and level-ups (`run/rewards`, `run/learning`, `run/items`, `run/levelup`)

- Status: accepted
- Date: 2026-10-12

## Context
Spec 1.11 ("Rewards, items and level-ups") adds what happens between a won fight and the next step: a rewards screen (skills or Words, items, crowns purses; rerolls), learning a card with a full hand, item swaps whose cards belong to the item, and level-ups after elite and boss fights. Until now a node result moved the run straight on. Events and merchants (M2 step 5) will reuse learning and item swaps. Code rule 10 asks for an ADR for the new run phases, the new content fields and the new modules.

## Decision
- **Content.** Skills, Words, weapons, armor and accessories gain an optional `rarity` (`RARITIES`: common, uncommon, rare; default common). An act gains `rewards`: tier → `{ kinds, rarity, crowns }` (`REWARD_KINDS`: skill, item, crowns; weights are integers ≥ 0 with one above 0; purse `0 ≤ min ≤ max`; no unknown keys). An act with `groups` needs a table for all four tiers. Rarities, kinds and tiers are data enums of the format, not content ids (code rule 2).
- **Node results carry the fight's tier.** `NodeResult.rewardTier` (set by `finishFight` to the group's tier on a win). `completeNode` refuses (`invalid_result`) a tier that isn't one or has no table in the current act. The run keeps it in `RunState.rewardTier` from the result until it moves on, including through a fall, so a revive runs the same after-node steps on the same stream.
- **New phases** `rewards`, `learning`, `levelUp`, each with its own plain-data field (`rewards`, `learning`, `levelUp`), null outside its phase. Order: rewards → learning (only when a card arrives with 5 cards) → level-up (elite and boss, `LEVEL_UP_TIERS`) → the usual advance, which clears the node and all of these. If nothing can be offered there is no rewards phase; if no stat can be raised there is no level-up. The node stays current through the three phases.
- **Commands and events.** `takeReward`, `skipReward`, `rerollRewards` (only through `consume(limits, "reroll", grant)`, code rule 7), `forgetCard`, `leaveCard`, `chooseLevelUp`; a bad index is `no_such_option`, any other phase `wrong_phase`, and a refused command changes nothing. Events: `RewardsOffered`, `RewardsRerolled`, `RewardTaken`, `RewardSkipped`, `CrownsGained`, `ItemEquipped`, `CardRemoved`, `CardOffered`, `CardLearned`, `CardLeft`, `LevelUpOffered`, `StatRaised`. Events carry copies, never the state's own objects.
- **Modules.** `run/rewards.ts` is the pure screen draw (pack, cards, picks, table, Intelligence bonus, rng): the first 3 options by kind weight among drawable kinds, then a rarity by weight among rarities with candidates left, then a candidate in pack order with equal chance; bonus options are skills or Words only. `run/learning.ts` gains, forgets and removes cards (`gainCard` is the one rule for "a new card arrives", also for item cards and, later, events, merchants and companions). `run/items.ts` swaps an item. `run/levelup.ts` draws the offer and raises a stat. `run/run.ts` keeps only the phase flow and the commands. `pickWeighted` became generic over its key type so the rewards draw reuses the run map's weighted draw.
- **Max HP has one formula.** Loadout assembly exposes `loadoutTotals(pack, picks, baseStats)` (final stats and 20 + 5 × final Vitality + items' HP); `assemblePlayer`, item swaps and level-ups all use it. An item swap or a level-up moves `maxHp` by the formula's change and HP by the same amount (HP stays in [1, max HP] after a swap), so only a Vitality gain or an item's Vitality/HP changes max HP, with the 0 floor applied.
- **Item cards are owned by the item, not by their origin.** A weapon's card is its Strike (the weapon id); an accessory's is its `grants`. On a swap the old item's card leaves if held, whatever put it in the hand, then the new item's card is gained like a new skill; a card already held is never gained twice.
- **Randomness.** Screens: `derive("rewards", actNumber, act, step, rerollIndex)` with the reroll number of the current screen (0 for its first draw); level-ups: `derive("levelup", actNumber, act, step)`. Nothing else in the run shifts with rerolls or with what was taken.

## Consequences
- Events and merchants can reuse `gainCard` + the learning phase and `equipItem`; a merchant's purchase may want its own after-step instead of `afterRewards`, which is internal today.
- `RunState` gains five fields; saves from before this change aren't loadable without a migration (saves are versioned from M4).
- The UI (M3) needs the comparison view before an item pick and the one-time warning before Strike is forgotten; neither is a rule, so neither is in the core.
- Placeholder rarities and Act I tables (and the placeholder reward-only items Warden Glaive and Drowned Plate and the skill Riposte) are tuned in M5 with the simulator.
